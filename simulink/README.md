# BattLock Simulink Verification & Co-Simulation

This folder contains the Simulink model that simulates the BattLock CAN
security flow, **plus** the integration scripts that connect the simulation
to the real BattLock Python implementation.

The model alone is a visualization. The integration scripts make it relevant:
CAN frames generated by Simulink are verified by the actual BattLock crypto
code, and the agreement between the two independent implementations is
reported as verification evidence.

Since the binary Simulink model (`Battlock_System2.slx`) currently implements
6 attack modes, the project now extends the verification flow to **12 modes**
by generating modes 6–11 directly from the real BattLock Python attack classes
and unifying them with the Simulink output for plotting and reporting.

## Files

### Simulink / MATLAB

| File | Purpose |
|------|---------|
| `Battlock_System2.slx` | The Simulink model (renamed from `Battlock_System-2.slx`; model names cannot contain `-`). Signal logging enabled on all key outputs. |
| `run_integration.m` | **One-command MATLAB driver**: export frames → verify with Python → plot + report. Start here when running MATLAB. |
| `export_frames.m` | Runs the model for the first 6 attack modes and exports the CAN frame stream to `frames.csv`. |
| `verify_battlock.m` | Runs the model alone across modes 0–5 (Simulink-only check). Writes `verification_plot.png` + `verification_report.csv`. |
| `make_integration_plots.m` | Reads `frames_verified.csv`, plots Python verdicts, writes `integration_report.csv`. |

### Python extension (modes 6–11 + unified reporting)

| File | Purpose |
|------|---------|
| `generate_extra_modes.py` | Generates `frames_extra.csv` for attack modes 6–11 using the real Python attack classes. |
| `verify_all_modes.py` | Unifies `frames.csv` (Simulink, modes 0–5) + `frames_extra.csv` (Python, modes 6–11), verifies every row with BattLock crypto, and writes `frames_verified_all.csv` + `verification_report_all.csv`. |
| `plot_all_modes.py` | Reads `frames_verified_all.csv` and produces `integration_plot_all.png` and `modes_overview.png`. |

### Generated artifacts

| File | Purpose |
|------|---------|
| `frames.csv` | Raw CAN frames exported from Simulink (modes 0–5). |
| `frames_extra.csv` | Frames for modes 6–11 generated by Python attack classes. |
| `frames_verified_all.csv` | Per-frame Python verdicts for all 12 modes. |
| `verification_report_all.csv` | Per-mode summary + Python/Simulink agreement. |
| `integration_plot_all.png` | 12-mode grid of Python verifier verdicts. |
| `modes_overview.png` | Summary bar chart of outcomes across all modes. |

Python side (`<repo>/integration/verify_frames.py`):
| File | Purpose |
|------|---------|
| `integration/verify_frames.py` | Legacy verifier for Simulink modes 0–5 only. |
| `simulink/verify_all_modes.py` | Recommended verifier for all 12 modes. |

## How the integration works

### Original flow (modes 0–5)

```
Simulink model (Battlock_System2)
   │  runs 6 attack modes, logs bus signals
   ▼
export_frames.m  ──►  frames.csv
   │
   ▼
verify_frames.py  ──►  frames_verified.csv
   │
   ▼
make_integration_plots.m  ──►  integration_plot.png + integration_report.csv
```

### Extended flow (modes 0–11)

```
Simulink model          generate_extra_modes.py
   │                           │
   ▼                           ▼
frames.csv  ─────────────  frames_extra.csv
   │                           │
   └───────────┬───────────────┘
               ▼
        verify_all_modes.py
               │
   ┌───────────┴───────────┐
   ▼                       ▼
frames_verified_all.csv  verification_report_all.csv
   │
   ▼
plot_all_modes.py  ──►  integration_plot_all.png + modes_overview.png
```

The verification logic mirrors the model blocks but is implemented in the
real BattLock Python code:

| Check | Simulink block | Python function |
|-------|----------------|-----------------|
| Replay counter | `Replay_Protection` (Unit Delay + `>`) | `crypto.counters.replay_protection.ReplayProtection.validate` |
| Signature | `Vehicle_Node` (`EXPECTED == SIGNATURE`) | expected = nonce + 100 |
| Injection | `Injection_Detection` (`voltage > 100`) | voltage > 100 |

The model's signature scheme is `signature = nonce + 100` (Bias block). This
is a documented placeholder for the full ECDSA flow implemented in the
Python orchestrator (`run_battlock.py`). The frame values, counters, and
thresholds are produced by Simulink; the *verification decisions* are made
by the real Python code.

## Requirements

- MATLAB R2025a with Simulink + Stateflow (for modes 0–5 only).
- Python 3.11+ with `cryptography`, `matplotlib`, and `numpy` installed.

## How to run

### Full 12-mode Python pipeline (no MATLAB required)

From the repo root:

```powershell
PYTHONPATH=. python simulink/generate_extra_modes.py
PYTHONPATH=. python simulink/verify_all_modes.py
PYTHONPATH=. python simulink/plot_all_modes.py
```

This regenerates `frames_extra.csv`, `frames_verified_all.csv`,
`verification_report_all.csv`, `integration_plot_all.png`, and
`modes_overview.png`.

### Original MATLAB-only flow (modes 0–5)

```matlab
cd <repo>
run_integration
```

## Attack modes

| Mode | Source | Attack | Expected result |
|------|--------|--------|-----------------|
| 0 | Simulink | None (baseline) | Auth OK, telemetry streams |
| 1 | Simulink | Replay (stale counter) | replay_detected raised, telemetry blocked |
| 2 | Simulink | Signature spoofing | Auth blocked, telemetry blocked |
| 3 | Simulink | Voltage injection (999 V) | injection_detected raised, telemetry blocked |
| 4 | Simulink | Signature dropping | Auth blocked, telemetry blocked |
| 5 | Simulink | Spoof + voltage injection | Auth blocked + injection_detected raised |
| 6 | Python | MITM telemetry tamper | injection / evasion detected |
| 7 | Python | Delay / reorder | replay detected due to out-of-order counters |
| 8 | Python | Fuzzing | malformed frame detected |
| 9 | Python | Session hijacking | replayed session ID flagged |
| 10 | Python | Threshold evasion | values near limits or fault_flags detected |
| 11 | Python | Certificate tampering | certificate verification fails |

Telemetry is gated on ACTIVE_SESSION (`state == 5`) AND no replay/injection
detected. Replay and injection detection feed the Telemetry gate, so a
detected attack stops telemetry as well as raising the dashboard flag.
